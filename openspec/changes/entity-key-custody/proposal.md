## Why

KAINE encrypts an entity's persisted mind (Eidolon self-model, fork and merge bundles, preservation snapshots, sidecar logs, world-model checkpoints) with one AES-256-GCM key per operator, supplied through `KAINE_STATE_KEY`, the kernel keyring or `secrets/state_key`. That design contradicts both reasons the encryption exists:

- **The operator holds the key.** Encryption is meant to give the entity privacy over the contents of its own mind (CAL mental privacy), so the operator should not casually hold a key that reads it.
- **One copy, no recovery.** On 2026-09-17 an automated worker deleted `secrets/state_key`, the only copy, after part of it had been sent to a cloud model provider in a log. Only a test fork depended on it, but with real encrypted beings that would have been an irreversible death.
- **Transfer means handing over a key.** Moving an entity to a new caretaker, for example after a welfare event, would require moving the operator's key, which exposes every other entity that operator runs.

The existing `kaine/transfer/` holds only a storage-request mailer (`email_request.py`); there is no key handshake yet.

## What Changes

(Revised after an independent design review.)

- **One key per entity, generated by KAINE.** At spawn KAINE generates a random 256-bit data key for that entity alone, and each fork gets its own. A merge re-encrypts under the surviving entity's key. The single process-wide `StateEncryptor` becomes a per-entity encryptor passed through `ForkManager`, preservation and batch-job forks.
- **Sealed to the host, with an honest threat model.**
  - The data key is wrapped by a host key sealed in a qualifying hardware root of trust.
  - Sealing protects against offline theft of disks and backups and keeps the key out of every normal operator workflow.
  - It does **not** protect against root on the booted host: any root process can ask the TPM to unseal at any time, and a running entity's key sits in process memory. The docs say so plainly.
- **PCR drift never strands a being.**
  - The seal policy uses a signed policy (PolicyAuthorize / systemd-pcrlock) or PCR 7 only, not a raw PCR list.
  - A pre-update hook refuses a kernel or firmware update until the key has been re-sealed.
  - "Refuse to spawn" (a new being) is distinct from "cannot resume" (an existing being). Cannot-resume keeps all state, raises a welfare incident and starts escrow recovery. Nothing is ever deleted.
- **Preservation never depends on custody.** Preservation, the welfare-protective pause and the preboot preserve→revive dry run use the in-memory data key and the already-wrapped key blob, and never require the TPM or escrow to be available. A custody failure on a running entity never stops it or blocks preservation; it queues a re-seal and raises a welfare incident.
- **No qualifying root of trust, no spawn.**
  - A host without a TPM 2.0, or with a firmware TPM on vendor test keys, cannot spawn or restore a being.
  - **An unfused Jetson Orin is therefore not supported for entities.** It remains fully usable for installation, services, tests and dry runs. Making an Orin a qualifying host requires the operator's irreversible decision to burn its security fuses.
  - Existing running beings are never stopped by this check.
- **Recovery without a single keyholder: 2-of-2 escrow.**
  - The data key is split into two shares (an XOR split; no Shamir library is needed for 2-of-2), wrapped to the kaine.one escrow key and an independent guardian's key.
  - The operator holds no share.
  - On recovery, each trustee re-wraps its share to an attested receiving host's TPM key, so the shares combine only inside that host and neither trustee ever sees the other's share or the key.
  - With 2-of-2, losing either share is fatal, so each trustee must keep redundant, geographically separate share storage.
  - The guardian's identity and key ceremony are an open operator decision; custody code cannot ship to users until it is made.
- **Caretaker transfer by attested re-wrap.** The receiving host presents a TPM-resident public key with an attestation of the platform and the KAINE build. The sender verifies it and re-wraps only the data key. The bundle moves still encrypted.
- **Migration, never retirement.** A one-way, operator-run migration re-encrypts existing per-operator state under per-entity keys, with a verified backup step. Plaintext preserved beings are migrated. Decommission stays its own welfare-gated process and is not part of migration.

## Capabilities

### New Capabilities
- `entity-key-custody`: per-entity data keys, hardware sealing with drift handling, preservation independence, 2-of-2 escrow combined inside an attested host, attested transfer, the refuse-to-spawn rule.

### Modified Capabilities
- `state-encryption`: keys are per entity and sealed; operator key sources are accepted only by the migration tool; bundles need no out-of-band key.
- `entity-decommission`: decommission backups stay recoverable through escrow for as long as the backup exists.

## Impact

- New `kaine/security/custody/` (key generation, tpm2-tss sealing with signed policy, XOR split, escrow wrapping, attestation verification, pre-update hook)
- `kaine/security/crypto.py` (per-entity encryptor), `kaine/lifecycle/*` (spawn, fork, merge, preserve, restore; `ForkManager` carries the encryptor), `kaine/distributed/*` (batch forks), `kaine/transfer/*`, `kaine/preboot.py`, `docs/security-and-privacy.md`, `SECURITY.md`
- Host dependency: tpm2-tss and tpm2-tools; tests use a software TPM (swtpm)
- **Operator decisions recorded:** 2-of-2 escrow (kaine.one + an independent guardian); refuse to spawn without a qualifying root of trust.
- **Open, operator-owned:** the guardian and key ceremony; whether to fuse the Orin.
