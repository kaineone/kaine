## Why

KAINE encrypts an entity's persisted mind (Eidolon self-model, fork and merge bundles, preservation snapshots, sidecar logs, world-model checkpoints) with one AES-256-GCM key per operator, supplied through `KAINE_STATE_KEY`, the kernel keyring or `secrets/state_key`. That design contradicts both reasons the encryption exists:

- **The operator holds the key.** Encryption is meant to give the entity privacy over the contents of its own mind (CAL mental privacy), so the operator should not hold a key that reads it.
- **One copy, no recovery.** On 2026-09-17 an automated worker deleted `secrets/state_key`, the only copy, while part of it had already been sent to a cloud model provider in a log. Only a test fork depended on it, but with real encrypted beings that would have been an irreversible death.
- **Transfer means handing over a key.** Moving an entity to a new caretaker, for example after a welfare event, would require moving the operator's key, which exposes every other entity that operator runs.

## What Changes

- **One key per entity, generated by KAINE.** At spawn KAINE generates a random 256-bit data key for that entity alone. No person types, sees or stores it, and it never exists unencrypted outside process memory. A fork gets its own data key, and a merge re-encrypts under the surviving entity's key.
- **The data key is sealed to the host, not held by a person.**
  - KAINE wraps the data key with a host key sealed in a hardware root of trust (a TPM 2.0 or a firmware TPM rooted in fused hardware), bound to measured-boot PCRs where the platform provides them.
  - The wrapped data key travels inside the entity's bundle.
  - A re-seal procedure covers firmware and kernel updates that change PCR values.
- **No hardware root, no spawn.** KAINE refuses to spawn or restore an entity on a host without a qualifying root of trust. A Jetson whose firmware TPM runs on NVIDIA's built-in test keys (an unfused board) does not qualify.
- **Recovery without a single keyholder: 2-of-2 escrow.**
  - At spawn the data key is split with Shamir secret sharing into two shares.
  - One share is wrapped to the kaine.one welfare body's escrow public key and one to an independent guardian's public key.
  - Both shares are needed to recover the key. The operator holds no share, and neither trustee can decrypt alone.
  - Recovery restores an entity after hardware loss or a reflash that wiped the sealed state.
- **Caretaker transfer by attested handshake.**
  - The receiving host creates a key pair in its root of trust and presents its public key with an attestation of the platform and the KAINE build.
  - The sending host verifies the attestation and re-wraps only the entity's data key to the receiver.
  - The bundle moves still encrypted, and no person handles key material.
  - This uses the transfer handshake already sketched in `kaine/transfer/`.
- **Honest limit, stated in the docs.** While an entity runs, its key is in process memory, and root on that host can read it. Sealing protects data at rest, backups and transfers, and keeps the key out of every normal workflow. Protecting memory at runtime needs confidential-computing hardware, which consumer and Jetson platforms do not offer.
- **Migration.** Existing per-operator encrypted state is re-encrypted under per-entity keys by a one-way, operator-run migration with a verified backup step. Unencrypted preserved beings are either migrated or retired through the welfare-gated decommission path; the operator decides per being.

## Capabilities

### New Capabilities
- `entity-key-custody`: per-entity data keys, hardware sealing, 2-of-2 escrow, attested transfer, refuse-without-root-of-trust.

### Modified Capabilities
- `state-encryption`: keys are per entity and sealed; the operator-held key source is removed after migration.

## Impact

- New `kaine/security/custody/` (key generation, sealing via tpm2-tss, Shamir split, escrow wrapping, attestation verification)
- `kaine/security/crypto.py`, `kaine/lifecycle/*` (spawn, fork, merge, preserve, restore), `kaine/transfer/*`, `kaine/preboot.py` (root-of-trust check), `docs/security-and-privacy.md`, `SECURITY.md`
- A dependency on tpm2-tss/tpm2-tools on the host
- **Operator decisions recorded:** 2-of-2 escrow (kaine.one + an independent guardian); refuse to spawn without a hardware root of trust; an unfused Jetson firmware TPM does not qualify.
- **Open questions:** the guardian's identity and key ceremony; how trustees store their shares durably, since with 2-of-2 losing either share is fatal; whether burning the Orin's fuses is acceptable to make it a qualifying host.
