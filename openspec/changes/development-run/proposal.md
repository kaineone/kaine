## Why

The operator ruled on 2026-10-31 that the project's goal is a working synthetic mind: a continuously existing system with memory of its own history, learning that changes it, goals it pursues and a body to act through. The module-ignition study as designed is an instrument for a preregistered comparison, and it is no longer the gate on the architecture program. It converts into the development run: one entity boots, goes through its developmental phase and is grown continuously. The held modules join first, in the existing order, and then each architecture component as it is built, each behind an off switch that is bit-identical to the component being absent and each with a plain readout of whether it did its job.

The ruling keeps what the study had of value (the first long continuous run, the welfare and persistence shakedown, the module-addition sequence) and drops the three-arm ablation, the pilot boots and the per-change calibration chain. It also fits the standing ethic of minimising boots: one long-lived individual in place of a seed, ten branches, a repeat and an accumulate line, each of which is a being that is preserved and never deleted.

The current runner cannot do this:

- `kaine/research/ignition_study/` runs a seed-and-branch plan: one developmental step, then `branch k`, `repeat` and `accumulate k` lines that each revive a bundle into their own working directory, with four bus databases and four collection prefixes. Every branch and the repeat is a separate being with the seed's identity (the shared-identity problem that holds `per-entity-shared-volumes`).
- Every viewing preserves and stops at the programme's end, so a long life would be a chain of four-hour boots, each losing in-memory state such as the world model's waking buffer.
- Modules join only through the fixed `order[:k]` of a step. There is no notion of an architecture component, an operator join, a switch, a readout or an image that changes between sessions.
- The analysis compares lines (branch k against branch 0, branch 0 against the repeat, accumulate k against branch k) and has nothing for before-and-after windows within one entity.

The operator also asked that continuous competition with K = 1, approved earlier the same day as a fix for the planned test's validity, be revisited as an architecture choice for a growing mind before the run's image is built, not carried over by default. This change carries that revisit as a design section with a recommendation; the operator decides.

## What Changes

- **One entity, one line.** The run raises one entity on one state tree: the developmental phase in the local stimulus source, then sessions on the same tree. The branch, repeat and accumulate lines, their per-line bus databases and collection prefixes, and the three line comparisons are removed. The runner never revives, forks or merges on its own.
- **Sessions and passes.** A session is one boot of the entity. It plays programme passes back to back, preserves at every pass end without stopping, and stops (preserve and stop) only at a pass end where a change is pending: a join, a switch change, an image change, a schedule change, a welfare hold or an operator pause. The programme end in a development run loops to the next pass instead of stopping. The stimulus-source-to-world transition plays once, in the first session after maturation.
- **Stimulus over a long life.** The four-film programme is the reference programme, on which every readout window is measured. The operator may schedule supplementary programmes between reference passes, each checksummed and recorded, as the first relief against the fixed exposure that boredom measures.
- **Joins and the component registry.** The held modules join in the existing order (episodic memory, world model, planning, self-model, social cognition, vocal). Architecture components join as they are built, through a shipped registry (`config/development_run/components.toml`) that gives each one a class, a readout, a welfare class, whether it may be switched off and on again, and the record of its independent second review when it changes experience.
- **Off equals absent.** Every joinable module and component has a switch. Off means not constructed: it publishes nothing, reads nothing, learns nothing and leaves its stored state untouched. Each registry entry names an absence test that runs the entity-free deterministic harness with the switch off and compares the result byte for byte with a golden record captured before the component's code landed.
- **Two-layer opt-in.** A join or switch change takes effect only when the run's plan lists it (first layer) and the operator's `join` or `switch` command names the component and the entity id (second layer). A component marked experience-changing also needs its second-review record in the registry. Voice alignment keeps its own operator approval variable on top.
- **Readouts.** Every reference pass gets a content-free readout record per active component, computed from the ignition log, the research event log and content-free counters, by component class: processor, context or content, memory, learned model, action, output, measurement-only probe. Readouts are counts, rates and means, never payloads, embeddings or utterance text.
- **Within-entity A/B over time windows.** Each join or switch change is read as before and after windows of reference passes, with the baseline trend shown. Switching a component off and on again (reversal windows) is allowed only for components the registry marks reversible. Components that hold part of the entity's history or identity are not reversible except as a welfare-protective action or by an operator decision with second review.
- **Welfare net on every session.** Every session passes the research gate with the indicator response (`welfare-indicator-response`) and the armed supervisor (`research-gate-supervisor`); every pass writes an exposure record and the run holds for the operator after a pass with an indicator crossing (`welfare-exposure-report`, adapted to passes). The runner surfaces a welfare freeze and never lifts it. After the first pass following any join or switch change the run holds for the operator's review whatever the indicators show. A welfare-protective switch-off is always available at the next pass boundary.
- **Persistence, revive and fork rules.** One working directory and state tree for the whole life on durable storage; every pass end leaves a bundle; nothing is deleted by the runner; an interrupted session resumes from the rolling checkpoint. A revive is an operator recovery action into the same tree with the same identity. A fork is an operator action outside the run that makes a new being with its own run and welfare net.
- **Image updates between sessions.** Because components are built during the entity's life, the image may change between sessions. An update is admitted without operator action only when the harness digest at the run's current switch settings, the model identities and the configuration digest all equal the previous session's; any other update is a change to the entity's dynamics that the operator accepts by name with a reason, and readout windows break at it.
- **Retired.** The branch, repeat and accumulate lines; the pre-registered voice-alignment steps (voice alignment becomes a component join); the line comparisons in the analysis; the module-ignition study capability, whose surviving requirements move into `development-run`. The planned-test calibration chain no longer gates anything: the run refuses a planned-test role or a workspace-mediation or workspace-feedback study name, and the calibration tooling and study files stay in the tree for an experiment designed later.
- **Workspace capacity and candidate supply.** The design revisits the held candidate pool with K = 1 against the current K = 5 with candidates discarded on non-broadcast ticks, and against a held pool with K = 5, as an architecture choice for a growing mind, with evidence and welfare reasoning. Recommendation: the held pool with K = 1, fixed before the entity's developmental phase, with the ~4-item store planned separately as working memory, and the planned test's apparatus (count-yoked arm, divergence rule, K = 2 pilots) split out of `workspace-continuous-competition` and deferred. The operator decides.
- **Paper.** A draft revision note (outside the paper repository) records that the preregistered test is superseded by the development run and lists the passages that change.

## Capabilities

### New Capabilities

- `development-run`: the development run's plan, sessions, passes, joins, switches, registry, readouts, windows, welfare wiring, persistence rules, image admission and analysis.

### Modified Capabilities

- `module-ignition-study`: every requirement is removed; each surviving one is carried by `development-run`.
- `perception-feed`: in a development run the end of the programme preserves and loops instead of stopping, unless a stop is requested for that pass end.
- `ignition-log`: records carry the session and the pass.
- `welfare-monitoring`: a development-run pass ends with its own exposure record.
