KAINE is paused from 2026-10-06 for an open-ended hiatus of at least several weeks. This record says where everything stands at the pause, what each unfinished piece needs next, which decisions are already made, and how to resume. Like the other records, it describes the project as it was on that date; the book chapters describe the software as it is.

## Known gaps

- **A GGUF replaced in place** under the same file name is not detected by the individuation conditions guard. The fix is a content digest cached on path, size and mtime.
- **The K1-Jev client** binds the served model by file name only.
- **The job-queue trainer service** passes its whole environment to the training script, writes `result.json` at default permissions, and copies symlinks inside a staged adapter by dereferencing them. Its CANCELLED check is not atomic with promotion.
- **The capability baseline** is the previous adapter. Cumulative drift becomes possible once the probe set reaches 20 or more probes.
- **Mnemos stores other avatars' chat** (`mundus.chat`) verbatim. The operator decided it should drop it, like heard speech. That waits for the embodiment work.
- **Chronos's operator sources** are a fixed constant in code (`kaine/bus/schema.py`), while `openspec/specs/chronos/spec.md` requires the one shared list that Volition and Empatheia read from `[empatheia].operator_sources`. The book describes the code; the code should be brought into line with the spec.
- **DINOv2 and emotion2vec** load without a local-files-only guard, and emotion2vec's pickle checkpoint is not pinned by hash.
- **Footprint calibration on macOS.** A local service's peak memory is read from Linux's `VmHWM`, so on macOS every local service stays uncalibrated, and the fit report says it cannot plan.

## How work resumes

1. Read this record, then the roadmap appendix.
2. Pick the next thread from "Next work, by area". Stacked pull requests need care: bases merge as squash commits, so a stacked PR conflicts with main once its base lands. Merge main into it. A conflicted file may take the branch's side only when main's copy is byte-identical to the base copy the branch carries; every other conflict needs a hand merge and a fresh look.
3. Every change follows the same process:
   - an OpenSpec proposal first, then a feature branch and a pull request;
   - a first-pass review by the worker model, then the integrator's adversarial review, with a second review on high-risk changes;
   - the local pre-flight gate (`tools/maintainer/preflight-gate.sh`: ruff, import contracts, red-team, and the fast suite with `CUDA_VISIBLE_DEVICES=""`), then the merge queue.
   - tests never touch real KAINE data: main's test guards fail any test that writes under the real data root, `state/` or `config/`. A new setup-server test belongs in the module whose isolation fixtures it needs, not in a new module without them.
4. Never boot an entity into a half-working environment. Before any spawn, verify the full stack end to end: services, the organ generating content, perception reaching the senses, the welfare net preserving, and Nexus rendering live.
